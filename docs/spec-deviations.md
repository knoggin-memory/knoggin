# Deviations from the spec

One line for every place where the build departed from the tech spec, with the reason.

- Engine, full-text index: the `tags` column holds a memory's plain tags only, not the `entity/`, `topic/` and `emotion/` label terms. At the reference commit recalld fills the FTS row from the stored record's `tags` (`src/derived_completion.rs` line 614, `fts.add(ns, *id, &record.summary, text.as_deref(), &tags)` with `tags` from `record.tags`). On a store in the native format, which every new data directory is, `POST /memories` goes through `single_store_versioned` and `store_api1::create` to the native writer, whose `NativeInsert` keeps the labels in their own fields and the plain tags in `InsertMemory.tags` (`src/storage/native_records.rs`: "Structured labels are persisted verbatim, never normalized into compatibility tags"). The merge of labels into tags in `handlers::create_memory` (`src/api/handlers.rs` lines 300 to 374) runs only for a store in the legacy format (`src/api/store_api1.rs` lines 54 to 63). The ranking fixture is the authority: with label terms 14 of the 40 queries came out in another order, without them all 40 match exactly.
- Engine, supersedes: a chain is walked through every successor (breadth first, 10 hops) and a cycle simply ends the walk, so a memory in a cycle can still be replaced by the newest member; recalld follows one successor and gives up on a cycle. The spec's "follow all of them" rule decides; no store made by Knoggin can hold a cycle.
- Engine, recall: a query vector of the wrong dimension or with a value that is not finite is treated as no vector (`degraded: model_unavailable`), since the engine has no error code for a host fault.
- Engine, context: a `topic` that is empty after trimming counts as no topic.
- Engine, recall trace: `suppressed` lists the candidates whose effective strength retrieval-induced forgetting lowered; recalld also listed neighbors that were not candidates.
- Engine, idempotency: `knoggin-core` builds the request-hash input (`store::request_hash_input`: name, zero byte, canonical JSON) but does not hash it; the host takes its SHA-256 with aws-lc-rs. The core may not depend on aws-lc-rs and the rules ban `sha2`, and a hand-written SHA-256 would be cryptography outside aws-lc-rs.
- Engine, signatures: `Store::create(id, model, now)` takes `now`, because the `default` namespace it makes needs a `created_at`.
- Engine, idempotency: an entry older than 24 hours counts as absent at lookup but is removed only once the operation has succeeded (with the bookkeeping change then), so that a failed write leaves the store unchanged.
- Engine, index rules: one more derived index, per namespace the `(created_at, id)` of every memory that is not a ghost. Automatic links and the duplicate report take their candidates from it and from the entity index instead of scanning the store; it is kept in place, rebuilt and compared by the property test like the others.
- Engine, saving: a vector passed to `store_memory` that is not valid for the store's model counts as one failed embedding (the memory is saved `Pending` with its failure count at 1, and the bookkeeping counter moves), as `apply_embedding` treats the same vector. Refusing the save instead would fail a valid memory over a fault of the host's embedder.
- Engine, list cursors: `knoggin-core` makes them base64url without padding (of `<millis>.<id>` for memories and `<count>.<tag>` for tags), so the host passes them through; a cursor that does not decode to one is `invalid_argument` on `cursor`.
- Engine, context: the topic is checked only by the recall that `context` runs, and an `invalid_argument` on that recall's `query` is reported on `topic`, the field the client sent.
- Engine, signatures: every write takes `ctx` and `now` as its last arguments, and so do `record_access`, `sweep`, `apply_embedding` (edge times), `on_open`, `export_page` (the header's `exportedAt`) and `import_record`, which also takes `OnConflict`; `ExportPage` holds `TransferRecord` values and the host writes each as one JSON line.
- Engine, access recording: `record_access` adds 1 to the bookkeeping counter only when it recorded at least one hit, so a call with only ghosts or unknown IDs does not trigger a snapshot.
- Testing, ranking fixture: recalld ran with `[graph] auto_link_threshold = 0.95` and `max_auto_links`, `max_entity_links`, `max_temporal_links` = 1. With its defaults every memory saved within an hour got 20 or more temporal links, every degree was at least 35, the fan was 0, and spreading activation and the connection bonus never acted. Ranking does not read these settings; they only decide which edges recalld makes, and the fixture stores recalld's edges as they are.
- Testing, ranking fixture: both supersedes chains are linear, because recalld refuses a second successor for one memory. The multi-successor rule is covered by unit tests only.
- Testing, ranking fixture: access counts come from `recalld ui`'s history totals, because recalld's REST memory route has none; edges and counts were read after the queries (checked unchanged, all queries ran with `recordAccess: false`).
- CI: the `deps` job (dependency review) is skipped while the repository is private, because GitHub's dependency review needs Advanced Security on a private repository.
- CI: cargo-deny is pinned at 0.21.0 and zizmor at 1.32.0, because 0.22.0 and 1.33.x were younger than 7 days on 2026-11-25. cargo-deny 0.21.0 accepts every key of `deny.toml`.
- CI: added `Swatinem/rust-cache` (saves on `main` only), per-job timeouts, a concurrency group that cancels superseded pull request runs, and a nextest `ci` profile with `fail-fast = false`. None is in the spec; each keeps CI fast or its failures complete.
- Root files: `LICENSE` came from `gh api licenses/agpl-3.0` (gnu.org timed out from the build machine); the text is unmodified.
- Root files: `dependabot.yml` lists npm, uv and docker before their manifests exist (milestones 4, 6 and 8).
- Root files: `THIRD_PARTY_NOTICES` is generated by `scripts/third-party-notices.sh` at release and image build and is not committed (it is in `.gitignore`).
- nextest: the override that puts `stack_*` binaries in the one-thread test group is commented out until the first stack test exists (milestone 6), because nextest refuses a `binary()` filter that matches no binary.
- Repository name: the spec's placeholder `knoggin/knoggin` is written `knoggin-memory/knoggin`, the organization's real name, everywhere, including the workspace `repository` field.
- Crypto, signatures: `LocalKeyProvider::wrap`, `token::new_api_key` and `token::random_token` return `Result<_, KeyError>`, because the system random source can fail and nothing on a request path may panic.
- Crypto, container: `seal` returns the concrete iterator `Sealer` (with a `Debug` that prints counts), not `impl Iterator`. Added `read_header_from` (reads one header from a stream, for the server's streamed download) and `Header::check_content_format(min, max)`, because the content format range is a constant of `knoggin-core::snapshot`, not of the container.
- Crypto, container: `open` returns `TooLarge` only after the first chunk has verified the header, so an `out_of_memory` lock is never decided on an unverified `content_len`.
- Crypto, key set: parsing refuses unknown fields and a key whose ID is not the SHA-256 rule applied to its bytes.
- Crypto, keychain: every write is read back and compared, because `security -i` exits 0 even when its command failed (checked on macOS 26 against a keychain file that does not exist). `secret-tool lookup` that exits 1 with no output at all counts as "not found"; any other failure is an error.
- Crypto, keychain: the key file and keychain code live in `knoggin-crypto` (the tab "Workspace and crates" puts reading the key source in the binary); the binary keeps the `auto` choice and `key-source.json`.
- Crypto, key file: reading follows a link and checks the file it names; only writes refuse links, as the spec says.
- Snapshot, decode: `Store::decode(content_format, content)` takes the header's `content_format`, because format-1 content carries no version number of its own. `snapshot::check_content_format` lets a host refuse a format before it decrypts anything.
- Snapshot, errors: `SnapshotError` has `Corrupt` and `FormatTooNew`; a format below `MIN_CONTENT_FORMAT` (only 0, which never existed) is `Corrupt`. `lock_reason()` gives the `store_locked` reason (`snapshot_unreadable` or `format_too_new`).
- Snapshot, decode checks beyond the spec's list: every section strictly sorted (so no repeats), tags valid and already lower-case, a ghost holds no text, tags or labels, the embedding state is `None` exactly for ghosts, history at most 32, stability, difficulty and edge weights finite, no edge loops, namespace IDs below `next_namespace_id`, names valid and unique ignoring case with `default` present, policies valid, idempotency keys valid, vectors valid (norm) and as many as the `Ready` memories. Value ranges (stability bounds, weight 0 to 1) are not checked, so a store whose float rounding lands just past a bound still opens instead of being locked.
- Snapshot, not persisted: `last_write_at` and `last_write_client` (the status page's last write) are not in format 1, so they are empty after a store is opened until its next write. The vector slot order is not kept either: vectors are written by ID, and no answer depends on the slot because every scan breaks ties by ID.
- Snapshot, encode: each postcard sequence is written item by item (the same bytes as postcard of the whole `Vec`, unit-tested), so encoding never holds a second copy of all text. A hidden `encode_as(written_by)` lets the frozen fixtures be compared byte for byte after the crate version changes.
- Engine, store: `Store` keeps `created_at` (set by `Store::create`), which the meta section's `created_ms` needs.
- Snapshot names: `SnapshotName` parses only the padded form (10 digits, `-`, 10 digits), so `knoggin admin restore --snapshot` takes the name as the snapshot list prints it, not `3-7`. It gives `file_name` (`<name>.kgs`, also the last part of the object key), `temp_file_name` (`<name>.kgs.tmp`) and `from_file_name`; the bucket prefix stays in `knoggin-server::storage::names`.
- Snapshot thinning: `thin` takes a slice of `SnapshotObject { name, last_modified }` and returns one label per object in the same order. The last hour is `now - 60 min < t <= now`, the last 24 hours likewise; a `last_modified` after `now` counts as `now`; `retention_days = 0` keeps no daily snapshot.
- Testing, property tests: the 50-word list, the operation generator and the harness moved from `tests/index_equivalence.rs` to `tests/support/mod.rs`, shared by the index-equivalence and snapshot round-trip tests; the 20 queries stay in `index_equivalence.rs`. The round-trip test also compares each decoded store's observable state (export lines, counters, embedding states, vectors by ID, idempotency table, size estimate) and its invariants.
- Testing, snapshot fixtures: the files are `empty.kgs`, `small.kgs` and `full.kgs`; their snapshot names are in the README beside them. The writer and the opening test are in `crates/knoggin-crypto/tests/snapshot_fixtures.rs`, because `knoggin-core` cannot depend on `knoggin-crypto`.
- Embeddings, ONNX Runtime source: `github.com/microsoft/onnxruntime` and its release downloads returned HTTP 404 on 2026-11-25, so `third_party/onnxruntime.toml` pins Microsoft's official NuGet package `Microsoft.ML.OnnxRuntime` 1.31.1 (SHA-512 checked against the nuget.org catalog). Each target table gains a `path` key naming the library inside that shared archive, and `scripts/fetch-onnxruntime.sh` extracts it with `unzip`.
- Dependencies, url 2.5.9: `reqwest` brought `url` into the lock for the first time on 2026-11-25, two days before 2.5.9 passed the publish-age rule, so it was taken by hand with `CARGO_RESOLVER_INCOMPATIBLE_PUBLISH_AGE=allow cargo update -p url --precise 2.5.9` as the Engineering rules say; the lock diff changed only `url` (2.5.8 to 2.5.9) and its own crate `form_urlencoded` (1.2.2 to 1.2.3).
- Embeddings, `model::ensure` is async (`tokio::fs`, hashing inside `spawn_blocking`), because the rules forbid blocking file work on runtime threads; `ModelSource` carries the back-off waits so the 429 test runs without a real clock.
- Embeddings, marker trust checks the models root, the model folder and the file (owned by this user or root, writable by nobody else); the spec names only the directory. New folders are created 0755 so a group-writable umask cannot make Knoggin's own markers untrusted.
- Embeddings, a local file error reports the reason `files_missing`; "250 MB" free space is read as 250,000,000 bytes and checked only when a file is missing; "three tries" on 429/503 is read as the first request plus three retries (1, 4, 16 s).
- Embeddings, `third_party/model-licence.txt` is the Apache 2.0 text with a header naming the model and its pinned commit, as the model page at that commit states.
- Crypto, keys: `DataKey::derive(info)` (HKDF-SHA-256, empty salt, 32 bytes) is the one HKDF helper; it is infallible, since HKDF refuses only outputs over 255 hash lengths. The state crate derives the field-seal, field-index and login keys with it.
- State, conformance: `testing::conformance(db, &clock)` also takes a `TestClock`, and every backend takes a `Clock` (`Arc<dyn Fn() -> i64>`), because the expiry cases (one at `expires_ms == now`) need a time the test controls. The database must start empty: the field-key case runs first, while no user exists. It covers every typed helper too, so Postgres and DynamoDB will run the helpers' rules as well. It lives in `pub mod testing` (the path the tab names), which tests of any crate can call; a `tests/support` module cannot be shared across crates.
- State, interface: a write that names one item twice, has an empty `pk` or `sk`, deletes with `Absent` or checks with `Any` is refused as `StateError::Invalid`, like more than 25 writes, so that the three backends agree (DynamoDB refuses the first two). An empty write list succeeds and does nothing.
- State, errors: one `StateError` for the interface and the helpers. Besides `Conflict` and `Unavailable` it has `Internal` (a panic in a blocking task), `Invalid`, `Corrupt` (a record, a sealed field or the state file that does not decode or open), `Key`, `SchemaTooNew`, `FieldKeyMissing`, `NotFound`, `AlreadyExists` (an app name), `LimitReached` (1,000 apps or key records; the caller answers `conflict`) and `StoreDeleted`.
- State, sealed fields: `Versioned<T>` keeps the stored document, and a write keeps a sealed string only when it opens, at the same item and field, to the value being written. A key's bookkeeping write therefore reads the `store-keys#` copy too (one more read per key and day) instead of sealing its name again.
- State, sessions: the `user-sessions#` index item gets the session's own expiry, which the tab does not give it, so that index items of ended sessions neither pile up nor count towards the 20.
- State, leader: the `leader/reconcile` item expires at its `until_ms`, so that `Absent` takes an expired leadership.
- State, helpers: `Users::update` refuses a change of identity or personal store and `Stores::update` a change of identity or name; names move with `Stores::rename` (record and name items in one write) and a lost personal store is replaced with `Users::replace_personal_store`. Lease park requests, `claims` and `abnormal_ends`, and a container's `stop_reason`, are private fields behind methods that enforce first-request-wins, cleared-only-by-parking, the 10-minute window and first-reason-wins. A park leaves the container fields of the lease as they were. `ParkReason` includes `shutdown` (a value of the park route) though `park_requested` never needs it.
- State, keys: rotating a revoked or unknown key is `NotFound`; revoking a revoked key changes nothing.
- State, bounds: the 1,000 apps and 1,000 key records are counted just before the write, so two creates at the same moment can end one over the bound. The bound only keeps partitions small, so that is accepted.
- State, erase: a store whose snapshot callback fails keeps its records and is counted in `EraseReport::stores_failed`; its user is not erased that run. The user that is never erased is found by its issuer `local` alone, because the subject is sealed and the lifecycle task holds no field key.
- State, local file: `LocalFileDb::create` (first run) writes an empty file as sequence 1, and `open` answers `None` when there is no state file (first run or `state_missing`, for the daemon to tell apart). A next name that already exists makes the write take the one after it, as snapshot rule 6 does. When the hard link succeeded but the directory sync failed, the new file is removed and the answer is `unavailable`. `knoggin state use-previous` has `local::previous_state_file` (path, write time, store IDs, key count of the newest file but one) and `local::set_aside_newest` (renames the newest to `<name>.bad`); asking for the yes is the command's. Master-key rotation of the file's key is `LocalFileDb::rewrap`, and of the field key and the store records `rewrap_master_key`.

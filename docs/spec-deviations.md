# Deviations from the spec

One line for every place where the build departed from the tech spec, with the reason.

- Engine, full-text index: the `tags` column holds a memory's plain tags only, not the `entity/`, `topic/` and `emotion/` label terms. At the reference commit recalld fills the FTS row from the stored record's `tags` (`src/derived_completion.rs` line 614, `fts.add(ns, *id, &record.summary, text.as_deref(), &tags)` with `tags` from `record.tags`). On a store in the native format, which every new data directory is, `POST /memories` goes through `single_store_versioned` and `store_api1::create` to the native writer, whose `NativeInsert` keeps the labels in their own fields and the plain tags in `InsertMemory.tags` (`src/storage/native_records.rs`: "Structured labels are persisted verbatim, never normalized into compatibility tags"). The merge of labels into tags in `handlers::create_memory` (`src/api/handlers.rs` lines 300 to 374) runs only for a store in the legacy format (`src/api/store_api1.rs` lines 54 to 63). The ranking fixture is the authority: with label terms 14 of the 40 queries came out in another order, without them all 40 match exactly.
- Engine, supersedes: a chain is walked through every successor (breadth first, 10 hops) and a cycle simply ends the walk, so a memory in a cycle can still be replaced by the newest member; recalld follows one successor and gives up on a cycle. The spec's "follow all of them" rule decides; no store made by Knoggin can hold a cycle.
- Engine, recall: a query vector of the wrong dimension or with a value that is not finite is treated as no vector (`degraded: model_unavailable`), since the engine has no error code for a host fault.
- Engine, context: a `topic` that is empty after trimming counts as no topic.
- Engine, recall trace: `suppressed` lists the candidates whose effective strength retrieval-induced forgetting lowered; recalld also listed neighbors that were not candidates.
- Engine, idempotency: `knoggin-core` builds the request-hash input (`store::request_hash_input`: name, zero byte, canonical JSON) but does not hash it; the host takes its SHA-256 with aws-lc-rs. The core may not depend on aws-lc-rs and the rules ban `sha2`, and a hand-written SHA-256 would be cryptography outside aws-lc-rs.
- Engine, signatures: `Store::create(id, model, now)` takes `now`, because the `default` namespace it makes needs a `created_at`.
- Engine, idempotency: an entry older than 24 hours counts as absent at lookup but is removed only once the operation has succeeded (with the bookkeeping change then), so that a failed write leaves the store unchanged.
- Engine, index rules: one more derived index, per namespace the `(created_at, id)` of every memory that is not a ghost. Automatic links and the duplicate report take their candidates from it and from the entity index instead of scanning the store; it is kept in place, rebuilt and compared by the property test like the others.
- Engine, saving: a vector passed to `store_memory` that is not valid for the store's model counts as one failed embedding (the memory is saved `Pending` with its failure count at 1, and the bookkeeping counter moves), as `apply_embedding` treats the same vector. Refusing the save instead would fail a valid memory over a fault of the host's embedder.
- Engine, list cursors: `knoggin-core` makes them base64url without padding (of `<millis>.<id>` for memories and `<count>.<tag>` for tags), so the host passes them through; a cursor that does not decode to one is `invalid_argument` on `cursor`.
- Engine, context: the topic is checked only by the recall that `context` runs, and an `invalid_argument` on that recall's `query` is reported on `topic`, the field the client sent.
- Engine, signatures: every write takes `ctx` and `now` as its last arguments, and so do `record_access`, `sweep`, `apply_embedding` (edge times), `on_open`, `export_page` (the header's `exportedAt`) and `import_record`, which also takes `OnConflict`; `ExportPage` holds `TransferRecord` values and the host writes each as one JSON line.
- Engine, access recording: `record_access` adds 1 to the bookkeeping counter only when it recorded at least one hit, so a call with only ghosts or unknown IDs does not trigger a snapshot.
- Testing, ranking fixture: recalld ran with `[graph] auto_link_threshold = 0.95` and `max_auto_links`, `max_entity_links`, `max_temporal_links` = 1. With its defaults every memory saved within an hour got 20 or more temporal links, every degree was at least 35, the fan was 0, and spreading activation and the connection bonus never acted. Ranking does not read these settings; they only decide which edges recalld makes, and the fixture stores recalld's edges as they are.
- Testing, ranking fixture: both supersedes chains are linear, because recalld refuses a second successor for one memory. The multi-successor rule is covered by unit tests only.
- Testing, ranking fixture: access counts come from `recalld ui`'s history totals, because recalld's REST memory route has none; edges and counts were read after the queries (checked unchanged, all queries ran with `recordAccess: false`).
- CI: the `deps` job (dependency review) is skipped while the repository is private, because GitHub's dependency review needs Advanced Security on a private repository.
- CI: cargo-deny is pinned at 0.21.0 and zizmor at 1.32.0, because 0.22.0 and 1.33.x were younger than 7 days on 2026-11-25. cargo-deny 0.21.0 accepts every key of `deny.toml`.
- CI: added `Swatinem/rust-cache` (saves on `main` only), per-job timeouts, a concurrency group that cancels superseded pull request runs, and a nextest `ci` profile with `fail-fast = false`. None is in the spec; each keeps CI fast or its failures complete.
- Root files: `LICENSE` came from `gh api licenses/agpl-3.0` (gnu.org timed out from the build machine); the text is unmodified.
- Root files: `dependabot.yml` lists npm, uv and docker before their manifests exist (milestones 4, 6 and 8).
- Root files: `THIRD_PARTY_NOTICES` is generated by `scripts/third-party-notices.sh` at release and image build and is not committed (it is in `.gitignore`).
- nextest: the override that puts `stack_*` binaries in the one-thread test group is commented out until the first stack test exists (milestone 6), because nextest refuses a `binary()` filter that matches no binary.
- Repository name: the spec's placeholder `knoggin/knoggin` is written `knoggin-memory/knoggin`, the organization's real name, everywhere, including the workspace `repository` field.
- Crypto, signatures: `LocalKeyProvider::wrap`, `token::new_api_key` and `token::random_token` return `Result<_, KeyError>`, because the system random source can fail and nothing on a request path may panic.
- Crypto, container: `seal` returns the concrete iterator `Sealer` (with a `Debug` that prints counts), not `impl Iterator`. Added `read_header_from` (reads one header from a stream, for the server's streamed download) and `Header::check_content_format(min, max)`, because the content format range is a constant of `knoggin-core::snapshot`, not of the container.
- Crypto, container: `open` returns `TooLarge` only after the first chunk has verified the header, so an `out_of_memory` lock is never decided on an unverified `content_len`.
- Crypto, key set: parsing refuses unknown fields and a key whose ID is not the SHA-256 rule applied to its bytes.
- Crypto, keychain: every write is read back and compared, because `security -i` exits 0 even when its command failed (checked on macOS 26 against a keychain file that does not exist). `secret-tool lookup` that exits 1 with no output at all counts as "not found"; any other failure is an error.
- Crypto, keychain: the key file and keychain code live in `knoggin-crypto` (the tab "Workspace and crates" puts reading the key source in the binary); the binary keeps the `auto` choice and `key-source.json`.
- Crypto, key file: reading follows a link and checks the file it names; only writes refuse links, as the spec says.
- Snapshot, decode: `Store::decode(content_format, content)` takes the header's `content_format`, because format-1 content carries no version number of its own. `snapshot::check_content_format` lets a host refuse a format before it decrypts anything.
- Snapshot, errors: `SnapshotError` has `Corrupt` and `FormatTooNew`; a format below `MIN_CONTENT_FORMAT` (only 0, which never existed) is `Corrupt`. `lock_reason()` gives the `store_locked` reason (`snapshot_unreadable` or `format_too_new`).
- Snapshot, decode checks beyond the spec's list: every section strictly sorted (so no repeats), tags valid and already lower-case, a ghost holds no text, tags or labels, the embedding state is `None` exactly for ghosts, history at most 32, stability, difficulty and edge weights finite, no edge loops, namespace IDs below `next_namespace_id`, names valid and unique ignoring case with `default` present, policies valid, idempotency keys valid, vectors valid (norm) and as many as the `Ready` memories. Value ranges (stability bounds, weight 0 to 1) are not checked, so a store whose float rounding lands just past a bound still opens instead of being locked.
- Snapshot, not persisted: `last_write_at` and `last_write_client` (the status page's last write) are not in format 1, so they are empty after a store is opened until its next write. The vector slot order is not kept either: vectors are written by ID, and no answer depends on the slot because every scan breaks ties by ID.
- Snapshot, encode: each postcard sequence is written item by item (the same bytes as postcard of the whole `Vec`, unit-tested), so encoding never holds a second copy of all text. A hidden `encode_as(written_by)` lets the frozen fixtures be compared byte for byte after the crate version changes.
- Engine, store: `Store` keeps `created_at` (set by `Store::create`), which the meta section's `created_ms` needs.
- Snapshot names: `SnapshotName` parses only the padded form (10 digits, `-`, 10 digits), so `knoggin admin restore --snapshot` takes the name as the snapshot list prints it, not `3-7`. It gives `file_name` (`<name>.kgs`, also the last part of the object key), `temp_file_name` (`<name>.kgs.tmp`) and `from_file_name`; the bucket prefix stays in `knoggin-server::storage::names`.
- Snapshot thinning: `thin` takes a slice of `SnapshotObject { name, last_modified }` and returns one label per object in the same order. The last hour is `now - 60 min < t <= now`, the last 24 hours likewise; a `last_modified` after `now` counts as `now`; `retention_days = 0` keeps no daily snapshot.
- Testing, property tests: the 50-word list, the operation generator and the harness moved from `tests/index_equivalence.rs` to `tests/support/mod.rs`, shared by the index-equivalence and snapshot round-trip tests; the 20 queries stay in `index_equivalence.rs`. The round-trip test also compares each decoded store's observable state (export lines, counters, embedding states, vectors by ID, idempotency table, size estimate) and its invariants.
- Testing, snapshot fixtures: the files are `empty.kgs`, `small.kgs` and `full.kgs`; their snapshot names are in the README beside them. The writer and the opening test are in `crates/knoggin-crypto/tests/snapshot_fixtures.rs`, because `knoggin-core` cannot depend on `knoggin-crypto`.
- Embeddings, ONNX Runtime source: `github.com/microsoft/onnxruntime` and its release downloads returned HTTP 404 on 2026-11-25, so `third_party/onnxruntime.toml` pins Microsoft's official NuGet package `Microsoft.ML.OnnxRuntime` 1.31.1 (SHA-512 checked against the nuget.org catalog). Each target table gains a `path` key naming the library inside that shared archive, and `scripts/fetch-onnxruntime.sh` extracts it with `unzip`.
- Dependencies, url 2.5.9: `reqwest` brought `url` into the lock for the first time on 2026-11-25, two days before 2.5.9 passed the publish-age rule, so it was taken by hand with `CARGO_RESOLVER_INCOMPATIBLE_PUBLISH_AGE=allow cargo update -p url --precise 2.5.9` as the Engineering rules say; the lock diff changed only `url` (2.5.8 to 2.5.9) and its own crate `form_urlencoded` (1.2.2 to 1.2.3).
- Embeddings, `model::ensure` is async (`tokio::fs`, hashing inside `spawn_blocking`), because the rules forbid blocking file work on runtime threads; `ModelSource` carries the back-off waits so the 429 test runs without a real clock.
- Embeddings, marker trust checks the models root, the model folder and the file (owned by this user or root, writable by nobody else); the spec names only the directory. New folders are created 0755 so a group-writable umask cannot make Knoggin's own markers untrusted.
- Embeddings, a local file error reports the reason `files_missing`; "250 MB" free space is read as 250,000,000 bytes and checked only when a file is missing; "three tries" on 429/503 is read as the first request plus three retries (1, 4, 16 s).
- Embeddings, `third_party/model-licence.txt` is the Apache 2.0 text with a header naming the model and its pinned commit, as the model page at that commit states.
- Crypto, keys: `DataKey::derive(info)` (HKDF-SHA-256, empty salt, 32 bytes) is the one HKDF helper; it is infallible, since HKDF refuses only outputs over 255 hash lengths. The state crate derives the field-seal, field-index and login keys with it.
- State, conformance: `testing::conformance(db, &clock)` also takes a `TestClock`, and every backend takes a `Clock` (`Arc<dyn Fn() -> i64>`), because the expiry cases (one at `expires_ms == now`) need a time the test controls. The database must start empty: the field-key case runs first, while no user exists. It covers every typed helper too, so Postgres and DynamoDB will run the helpers' rules as well. It lives in `pub mod testing` (the path the tab names), which tests of any crate can call; a `tests/support` module cannot be shared across crates.
- State, interface: a write that names one item twice, has an empty `pk` or `sk`, deletes with `Absent` or checks with `Any` is refused as `StateError::Invalid`, like more than 25 writes, so that the three backends agree (DynamoDB refuses the first two). An empty write list succeeds and does nothing; the file backend writes no new state file for it (`LocalFileDb::create` writes its first, empty file itself).
- State, errors: one `StateError` for the interface and the helpers. Besides `Conflict` and `Unavailable` it has `Internal` (a panic in a blocking task), `Invalid`, `Corrupt` (a record, a sealed field or the state file that does not decode or open), `Key`, `SchemaTooNew`, `FieldKeyMissing`, `NotFound`, `AlreadyExists` (an app name), `LimitReached` (1,000 apps or key records; the caller answers `conflict`) and `StoreDeleted`.
- State, sealed fields: `Versioned<T>` keeps the stored document, and a write keeps a sealed string only when it opens, at the same item and field, to the value being written. A key's bookkeeping write therefore reads the `store-keys#` copy too (one more read per key and day) instead of sealing its name again.
- State, sessions: the `user-sessions#` index item gets the session's own expiry, which the tab does not give it, so that index items of ended sessions neither pile up nor count towards the 20.
- State, leader: the `leader/reconcile` item expires at its `until_ms`, so that `Absent` takes an expired leadership.
- State, helpers: `Users::update` refuses a change of identity or personal store and `Stores::update` a change of identity or name; names move with `Stores::rename` (record and name items in one write) and a lost personal store is replaced with `Users::replace_personal_store`. Lease park requests, `claims` and `abnormal_ends`, and a container's `stop_reason`, are private fields behind methods that enforce first-request-wins, cleared-only-by-parking, the 10-minute window and first-reason-wins. A park leaves the container fields of the lease as they were. `ParkReason` includes `shutdown` (a value of the park route) though `park_requested` never needs it.
- State, keys: rotating a revoked or unknown key is `NotFound`; revoking a revoked key changes nothing.
- State, bounds: the 1,000 apps and 1,000 key records are counted just before the write, so two creates at the same moment can end one over the bound. The bound only keeps partitions small, so that is accepted.
- State, erase: a store whose snapshot callback fails keeps its records and is counted in `EraseReport::stores_failed`; its user is not erased that run. The user that is never erased is found by its issuer `local` alone, because the subject is sealed and the lifecycle task holds no field key.
- State, local file: `LocalFileDb::create` (first run) writes an empty file as sequence 1, and `open` answers `None` when there is no state file (first run or `state_missing`, for the daemon to tell apart). A next name that already exists makes the write take the one after it, as snapshot rule 6 does. When the hard link succeeded but the directory sync failed, the new file is removed and the answer is `unavailable`. `knoggin state use-previous` has `local::previous_state_file` (path, write time, store IDs, key count of the newest file but one) and `local::set_aside_newest` (renames the newest to `<name>.bad`); asking for the yes is the command's. Master-key rotation of the file's key is `LocalFileDb::rewrap`, and of the field key and the store records `rewrap_master_key`.
- recalld import, forgotten memories' edges: recalld keeps the edges of a forgotten (tombstoned) memory. The reader leaves out every edge with a forgotten end and counts it in `edgesSkipped`, so that a normal recalld store does not import with one error line per such edge; an edge to a memory that is missing for another reason is still yielded and reported by the import route, as the spec says.
- recalld import, labels "when the record has none": read as a record with no labels at all (version 1, or a schema whose three lists are all empty); then every `entity/`, `topic/` and `emotion/` tag becomes a label of that kind (as recalld's own `StructuredLabels::from_legacy`). A record with any label keeps the other prefixed tags as tags unless they equal the prefix plus a label in lower case.
- recalld import, reader error lines: a memory record that does not decode, has `required_features`, names an unknown namespace, has a time outside Knoggin's range, or whose text fails its length or CRC32 check is left out and listed in `Import::skipped` (table, memory ID, reason; never text) and counted in `errors`; the rest goes on. A namespace record that does not decode stops the whole import, because every memory of it would fail.
- recalld import, refusals beyond the spec's list: the given directory may not be a symbolic link (as recalld's own `StoreOwnership` refuses), a lock file that is a link is refused, and the run folder may not be in or beside the recalld directory (`RunDirInside`), checked before anything is created. Each file is opened after an `lstat`, and the open file's device and inode must match, so a link swapped in between is refused too. The shared locks are held until the copies are read, so recalld cannot start in the middle.
- recalld import, access history: Knoggin's limit of 32 events is applied by keeping the newest 32 after kind 3 is dropped (recalld's own limit is also 32).
- recalld import, lines: `savedBy` and `client` are written as `null` (the route records `import` anyway); a ghost's tags and labels are written as empty lists.
- recalld import, API: `knoggin_import_recalld::read(data_dir, run_dir, now)` reads the whole store into memory and deletes the copies before it returns, then hands back `Import { records, summary, skipped }`; the plaintext copies therefore exist only while the reader runs, not for the whole import. `Summary` serializes as the `--json` shape; the command replaces `edges` with the route's accepted edge lines and adds the route's error lines to `errors`.
- recalld-data fixture, `exportedAt` is masked as `null` in `expected-export.jsonl`, so the file stays a valid export file. `expected-counts.json` was made by feeding the lines to `knoggin_core::Store::import_record` on a fresh store (the import route's engine call), because the `knoggin` binary and its daemon do not exist yet; the milestone-4 CLI test must compare the real command's output with the same file.
- recalld-data fixture, what recalld 2.2 cannot make through its API, and is covered by unit tests instead: two namespace names that differ only in case (recalld refuses the second with `NAMESPACE_EXISTS`), version-1 records, the `legacy_access_v1` lifecycle (every new namespace is on explicit feedback), access kind 3, edge types 3 and 4, and hand-made associative edges. The fixture's `default` and `personal` namespaces carry an adopted inherited multiplier (1.0), which becomes `decayRateMultiplier: 1.0`.
- recalld-data fixture, size: recalld's redb files are preallocated (3.6 MB each for `meta.db` and `edges.db`, mostly zeros; redb's `compact()` only brings them to about 3 MB), so the directory is 7.3 MB on disk but about 64 KB compressed in git. It holds every file recalld wrote, `recalld.lock` and the derived `fts.db` included.
- recalld-data fixture, the script's check against recalld's own statistics compares namespaces, memories by phase, forgotten memories and edges read (lines plus skipped) with the sum of recalld's `edgeCount`, which counts only edges whose source is live; the forgotten memory is therefore saved first, so that it has no edges of its own.
- recalld import, redb: the lock resolves `redb = "2.6"` to 2.6.4; recalld at the reference commit locks 2.6.3, the same file format.
- HTTP, modules: `knoggin-http` adds a module `trace` (the UUIDv7 `MakeRequestId`, the request span with the matched route and request ID, and the `observe` middleware that logs one line and counts `knoggin_requests_total` / `knoggin_request_seconds`), because both the edge layer and a container's store layer need them and the module table has no home for them.
- HTTP, signatures: `store_layer(host)` keeps its one argument; the `limits` it needs (`body_bytes`, `request_timeout_ms`, `store_concurrency`) travel in `HostConfig::limits` (`settings::StoreLimits`). `settings` holds only the store layer's keys so far; the edge adds its own.
- HTTP, operations: every memory operation is a method of `StoreHost` (`host::ops`, `host::transfer`) that both REST and MCP call, so the namespace fill, the request hash, idempotency, the duplicate check, the query vector and access recording are written once. Idempotent writes return `host::Reply<T>` (`Fresh` or `Replayed(bytes)`).
- HTTP, export: the store layer sets no `Content-Disposition`, because the store's name lives in the state database, which the store layer does not read; the edge layer sets it with `store_api::export_file_name`. The store layer accepts the `store` query parameter and ignores it (the edge resolves and checks it). The per-user caps (2 exports, 2 imports) and the "third export is `rate_limited`" test belong to the edge layer and are not built here.
- HTTP, export: when the slow-client rule ends an export, the producer stops and frees the store and its request permit at once; the connection itself closes only when hyper next polls the body, because a client that reads nothing keeps hyper from polling it.
- HTTP, import: an import whose body moves no bytes for 60 seconds answers `timeout`; the lines applied before stay applied (a resend skips them). The answer keeps at most 10,000 error lines (`MAX_IMPORT_ERRORS`), so a huge file of bad lines cannot grow the answer without bound. Blank lines are skipped (they count in line numbers, not in `imported` or `skipped`). An error line's message starts with `line <n>:`.
- HTTP, import over the budget: the check runs per memory line against the room left when its batch started (batches of 256 lines or 1 MiB); over the hourly upload budget every line of the following batches is `rate_limited`.
- HTTP, writes while the upload budget is used up answer `rate_limited` with `Retry-After: 60` (tab "Server"), forgets included: the rule says the store takes no more writes.
- HTTP, dry runs (policy, namespace delete, batch forget) run under the write gate and the write lock (the engine methods take `&mut`) but are never refused by the memory budget and never clear `full`.
- HTTP, JSON bodies: an empty body counts as `{}`, so `POST /v1/memories/{id}/reinforce` and `/similar` work without a body; the content-type check applies only to a non-empty body. A request without a `RequestContext` (a wiring bug) answers `internal`, without a request ID.
- HTTP, metrics: a snapshot that cannot be read at open is counted in `knoggin_snapshot_failures_total`, because the metrics list has no separate read-failure metric.
- HTTP, model: the queue worker embeds only while the loaded providers' identity equals `HostConfig::model` (the identity every open store adopts), so a job can never loop on a model mismatch.
- HTTP, embedder: the two OS threads end when the `Embedder` (and with it the channel senders) is dropped, after the text they are on; they are not joined, because joining could block a runtime thread for the length of one embedding.
- HTTP, `LocalBackend`: a store with no record, or one marked deleted, opens as `BackendError::Deleted`; a wrapped key that does not unwrap (unknown master key or the wrong one) locks with `master_key_missing`. "A record is also corrected when its store is opened and they differ" is not done: the counts are known only after the decode, and the next save's `flush_records` corrects the record.
- HTTP, `LocalBackend` retention keeps the name it last recorded (from the record at open, then from each flush) as "the file the record names as newest".
- HTTP, panic hook: `panic::location_line` (the formatted line) is public beside `log_location`, so that a test can check the line without capturing stderr.
- HTTP, tests: the host's snapshot-timing tests run on paused Tokio time across `spawn_blocking` (Tokio does not auto-advance while a blocking task runs); they never load the model, so no test on paused time crosses the embedding threads.
- MCP, configuration: `McpConfig { source_url }` lives in `HostConfig::mcp` (default: the workspace `repository`, as the setting's default), because `store_layer(host)` keeps its one argument and mounts `/mcp` itself; the instructions' `{web_url}` is `HostConfig::web_url`, which already has the meaning the MCP tab gives (absent on a local install without `public_url`).
- MCP, sessions: a session is bound to the endpoint as well as to the store and the API key, so naming a `/mcp` session on `/mcp/plugin` gets the 404 of an unknown session. A session holds no negotiated version: nothing reads it after `initialize` answers. Session IDs are 32 random bytes from aws-lc-rs as 64 hex characters.
- MCP, `initialize`: its params must carry `protocolVersion`, `capabilities` and `clientInfo`; without them it is `-32602` and no session is made (recalld filled in defaults when `params` was absent). `notifications/initialized` sent with an `id` is `-32600`.
- MCP, current revision: `ping` and `initialize` that carry the current `_meta` answer `-32601`, as recalld does (both were removed in `2026-07-28`); `ping` without `_meta` is served.
- MCP, HTTP statuses: recalld's are kept: 400 for `-32700`, `-32600`, `-32602` without a session and `-32020`/`-32022`; 404 for an unknown session; 200 for every other JSON-RPC answer; 202 for every notification, without a session lookup or a `_meta` check. A body over the limit (413), the timeout (504), `GET` (405 with `Allow: POST, DELETE`) and `DELETE` without `Mcp-Session-Id` (405) or of an unknown session (404) answer with the REST error shape, because they happen outside the JSON-RPC layer. A message whose `jsonrpc` is not `"2.0"` or that is not a request object is `-32600`.
- MCP, tool errors: every `ApiError` the host returns (`store_locked`, `unavailable`, `rate_limited` and the rest) is a tool error with `isError`, without `Retry-After`. A credential without `memory:write` calling a writing tool gets `permission_denied` before its arguments are checked; a name that is not in the endpoint's set is `not_found`. When serde does not name the field of a wrong type, `field` is `arguments`.
- MCP, schemas: the `/mcp/plugin` input schemas are the `/mcp` ones without `recordAccess`, and its parser refuses `recordAccess` as an unknown argument. An output schema that utoipa writes without a top-level `type` (the untagged `RecallResponse`, the flattened `Context`) gets `type: object`, which MCP requires. utoipa does not collect the schemas of a generic type's parameter (`Page<T>`, `Items<T>`, `BatchResult<T>`), so they are added by hand before the `$ref`s are replaced.
- MCP, the client list: each open store keeps its 32 client names in `OpenStore`, noted in `StoreHost::open_for` on every request that carries `ctx.client`; read with `StoreHost::clients`.
- MCP, the batch test: the 100 full-size memories are saved with the model not loaded, so that 6.7 MB of text is not embedded while the other tests run. `store_routes::every_route_answers_success` now waits for the embedding queue before its similar search; under the load of the added tests it raced the queue and failed now and then.
- MCP, `rmcp`: the lock resolved 3.11.0 (minimum 3.10). As a dev-dependency it brings `chrono` and `sha2` into the lock, for the interop test only; no Knoggin code uses them.
- MCP, stdio: only the HTTP side is built; the `knoggin mcp` bridge and its tests belong to the binary (milestone 3, later).
- Edge, internal headers: the check on client `Knoggin-*` headers runs on the Unix socket too, although the tab lists it among the browser checks the socket skips. No client sends them, and one rule everywhere is simpler and stricter.
- Edge, first-byte timeout: the wait for a connection's first bytes is a one-byte peek (`TcpStream::peek`; on the socket `rustix::net::recv` with `PEEK`, hence rustix's `net` feature), because on macOS tokio's `readable()` reported a fresh socket ready at once and hyper-util's automatic builder then waited without a limit.
- Edge, OpenAPI: the store routes' handlers live in `store_api`, so their annotations sit on documentation-only stubs in `edge::openapi`; the control and mode routes carry theirs on their handlers. `/mcp` is not in the document (the REST tab does not list it). The committed copy is refreshed by the ignored test `write_openapi`.
- Edge, Store shape on the daemon: only `memoryCount` is read from an open store (the host's report has no other figure); `namespaceCount`, `lastWriteAt` and `lastWriteClient` come from the record as of the last `flush_records`.
- Edge, session route with an API key: `personalStoreId` is `null` (the tab does not say), so a key learns nothing of the user's other stores.
- Edge, path IDs that are not UUIDs answer `invalid_argument` on `id`; an API key whose store record is gone answers `unauthenticated`.
- Edge, `GET /v1/users` cursor: the last user's ID in its simple form (32 hex digits), which is base64url text.
- Edge, the fixed listener's bucket: a request without any credential is charged once, at step 1; a request whose credential is refused is charged at the refusing step, the session route included. "A cookie" in step 1 is read as a cookie that the mode reads: in mode `none` a cookie is ignored (step 8), so a request with only a cookie is charged at step 1 like one without any credential.
- Edge, `Cache-Control`: every API answer carries `no-store`. The web UI's files (milestone 4) have their own rule: `_app/immutable/` files are `public, max-age=31536000, immutable`, other files `no-cache`, and `index.html` `no-store`; on the daemon's local web listener every file is `no-store` (see "UI, serving").
- Edge, local routes: `POST /v1/local/browser-code` off the socket, `POST /v1/local/session` and `POST /auth/logout` off the web listener answer `not_found`; logout on the web listener with another credential than a local web session answers `permission_denied`.
- Edge, account deletion on a local install also ends the other local web sessions (the tab says "other sessions end").
- Edge, settings: `EdgeConfig` is a plain struct in `edge` that the binary fills, not a `serde` type in `settings.rs`.
- Edge, locked mode: `local::locked_router` runs the browser checks without `server.public_url`, so while locked a tunnel's address is refused; only the loopback names pass.
- Edge, not built in milestone 3: the cap of 10 event streams per user and their 60-second re-check (the stream route comes in milestone 4; export and import are re-checked), removing old `open-*.html` files (with `knoggin open`, milestone 4), the router's per-address and per-user buckets and trusted proxies (milestone 6).
- Binary, `knoggin start`: the child's session of its own comes from a hidden flag, `knoggin daemon --new-session`, with which the daemon calls `setsid()` first; `Command::pre_exec` would need `unsafe`. `start` waits at most 60 seconds for `/healthz` (the tab gives no bound).
- Binary, command tree: the server commands (milestone 6) are left out; `admin snapshot inspect | export` are in, because a locked local install needs them. `knoggin init` belongs to the Python package.
- Binary, `config check --json`: one flat object keyed by the dotted setting path in `snake_case` (`"auth.mode"`), because config keys are `snake_case`, with each value as its JSON value (string, boolean, number or array) and a secret as the string `[set]` or `[not set]`; settings without a value are not listed. Range checks cover `limits`, the session times, `retention` (1 to 3650 days) and `metrics.bind`; the server settings are checked in milestone 6.
- Binary, `knoggin status --json`: `{ running, address, model, masterKeySource, stores: [{ id, name, kind, status, memoryCount, state, lockedReason }] }`, from `GET /v1/stores` and each store's status route; exit 4 also when the whole install is locked.
- Binary, `knoggin state use-previous --yes` skips the question, for scripts and tests. `knoggin model verify --json` is `{ dir, graph, weights, tokenizer, library }`; it hashes every file whatever its marker says, then loads the library and one query session.
- Binary, `knoggin import` and `import recalld` exit 1 when the route reported error lines (the counts are still printed).
- Binary, locked mode: the listeners keep one router whose inside is swapped from `local::locked_router` to the whole API once the key and the state file can be read; the model starts only then.
- Binary, start-up order of step 8: the fixed and web TCP listeners, then `metrics.bind` and the stop-signal handlers (a failure of either is a start error, before anything serves), then the install (step 7's model start comes here, because the edge needs the bound address), then the Unix socket, then `{ pid, address }` in the lock file, and only then do the listeners serve. So a daemon that cannot take its port is never found on the socket, and once `/healthz` answers the lock file is complete. The lock file has mode 0600. `open-*.html` files older than 60 seconds are removed by the daemon's minute task.
- Binary, a detached daemon (`start`, `mcp`, `open`): its standard error is appended to `logs/daemon.log` rather than `/dev/null`, so a start failure, even one before logging starts, and the panic hook's location line land there; such a daemon logs to the file only, so no line is written twice. After a rotation its standard error still points at `daemon.log.1` (a `ponytail` note marks it). `spawn_detached` passes `--log-level` along with `--config` and removes `KNOGGIN_API_KEY` from the child's environment.
- Binary, start-up step 3: an existing `local.master_key_file` that is not a regular file of this user, or has a permission bit for group or others, stops the start (exit 1, with the `chmod` hint) whatever source `key-source.json` names, instead of locking the install as `master_key_missing`. The owner check is unit-tested only; a test cannot make a file of another user.
- Binary, `knoggin model fetch` without `--dir` refuses when `model.download` is false, since then nothing is written to `model.dir`. `knoggin state use-previous --json` without `--yes` exits 2, because the question cannot be part of JSON output.
- Binary, `Config` and `Auth` have a hand-written `Debug` that prints the bind, the sign-in mode, the log settings and counts, never an email, a subject or a path.
- Binary, tests: the marker test expects the refusals where a one-user daemon has no success path: `DELETE /v1/users/{id}` on the one user is 400 (no one removes themselves), `POST /v1/users/{id}/undelete` is 410 while the account is deleted (admin routes refuse a deleted account) and 409 when it is not, and `GET /v1/admin/stores/{id}/snapshots` is 404 (a server route). It searches for the master keys and the data key of every snapshot and of the state file in hex and base64; the field key is not searched. Locked mode is checked on every path and method of `docs/openapi.json` and the MCP endpoints. "Without test mode the real model is used" is a process test with `model.download = false` and no files, which reports the real identity as `unavailable: files_missing` and writes nothing.
- Binary, `knoggin key import`: replaces the set in the recorded source; when that source is a keychain tool this machine lacks, it picks a source as `auto` does. `knoggin key rotate` reads the set from its source twice (the old provider and the set it rotates), because `MasterKeySet` is not `Clone`.
- Binary, stdio bridge: built, with its tests (`crates/knoggin/tests/bridge.rs`). It handles one message at a time (a `ponytail` note marks the limit). After it starts a daemon it keeps trying for 10 seconds even if that daemon has already exited.
- Binary, runtime: commands run on two worker threads; the daemon takes Tokio's default.
- HTTP, opening a store: the load runs as a task the host owns (`shutdown` stops it), and every request for the store waits on it, so a request that times out leaves the load running and a second request starts no second load. A store whose load is running reports `waking`; a failed load removes its entry before the waiters see the error, so the next request starts afresh.
- HTTP, closing a store: a request that arrives while its store is being closed waits until the final snapshot is written and then opens the store again (or goes on if the save failed and the store stays open); it is not refused. A close waits for every request in flight, an export included, and for the write gate. A bookkeeping write of the host's own tasks (an embedding result, the sweep) that finds the store already closed answers `unavailable` and is lost: the memory stays `pending` in the snapshot and is embedded again after the next open.
- HTTP, `BackendError::Internal`: a panic in a backend's own blocking work (for `LocalBackend`, reading the store folder or writing a snapshot file) is `internal`, as the rule on `JoinError` says; a cancel stays `unavailable`. A snapshot that fails with it is retried with the usual back-off.
- HTTP, `out_of_memory`: the lock is kept for the life of the host (the container); neither a request nor the status route tries the store again. The local daemon has no budget and never sets it.
- HTTP, panics: a panic in a read answers `internal` and keeps the store open with its unsaved changes; a panic in a write still drops the store unsaved. A poisoned lock seen by a read still drops the store (only a write can poison it).
- HTTP, import parsing: each batch of lines (and the header line) is parsed in one `spawn_blocking` task before the batch takes the write gate, so the write lock is not held while JSON is parsed; the line splitter remembers how far it has looked for a newline, so a long line that arrives in small chunks costs linear time.
- HTTP, embedding worker: once the model-state sender is gone the worker waits only for work (and its 30-second timer); `Embedder::subscribe` marks the current state seen, because a clone of the embedder's own receiver counted every earlier change as new and woke at once. The no-spin test counts the worker's idle waits over 200 ms of real time, since a spinning worker would keep paused time from moving.
- Edge, credential kinds: every match on `edge::Credential` names each kind, with no `_` arm, and the steps only an API key takes go through `Credential::api_key`, so a new kind (OAuth tokens and cookie sessions, milestone 5) fails to compile until each site decides what it reaches.
- Edge, local web session times: the 60-second code lifetime and the 24-hour idle limit are measured on the edge's wall clock (`EdgeParts::clock`, milliseconds since 1970), passed in by the caller, because a monotonic clock does not advance while macOS sleeps; a wall clock set back can lengthen a session by the same amount.
- Edge, step order on the control routes: the per-user in-flight cap is taken as part of step 12 ("by user"), with the per-credential bucket, so both run before step 13's permission and admin checks; a refused request holds the cap only while its refusal is written.
- Edge, `Knoggin-Key-Expires`: set on every answer to a request whose API key passed steps 6 to 11 (control routes and `GET /v1/session` included, and refusals at steps 12 and 13 and in the store layer), but not when step 10 or 11 refuses the request, where the edge has not accepted the key.
- Edge, `Authorization` scheme: `Bearer` is matched without regard to case (`bearer`, `BEARER`), as RFC 9110 has it; the value is trimmed, and an empty value is a malformed header (`unauthenticated`).
- Edge, the way out: the store layer's `normalize` and the edge's `finish` share `error::shape_answer` (bare library answers become `ApiError`s, the request ID goes into error bodies, `Cache-Control: no-store`); `finish` adds only the `Knoggin-Request-Id` header and the browser headers. An MCP answer (marked `mcp::Answered`) therefore keeps its JSON-RPC body through the edge too, such as the 404 of an unknown session, which the edge used to rewrite as a REST `not_found`.
- Edge, OpenAPI names of the generic shapes: utoipa 6 names `Page<T>`, `Items<T>` and `BatchResult<T>` only as `Page_Memory` and so on, and those types live in `knoggin-core`, so `edge::openapi` renames them after generating the document (in the components and every `$ref`): a page is `<Item>Page` (`MemoryPage`, `TagCountPage`, `UserPage`), an unpaged list `<Item>List` (`StoreList`, `ApiKeyList`, `NamespaceList`, `SimilarHitList`), and the batch answer `BatchResult` with `BatchItemResult`, the SDK's name. `Sensitive` fields are `#[schema(inline)]`, so no `String_String` schema appears.
- HTTP, work on large inputs: the request hash of a keyed write, the duplicate check's content checks and document text, and the serialization of each export page run in `spawn_blocking` (an export page outside its read lock). Each costs one blocking-pool hop, also for small requests; a write without `Idempotency-Key` makes none for the hash.
- State, master-key rotation: `rewrap_master_key` pages through the user directory itself and skips an item whose user record is gone, so such an item can neither shorten a page nor end the walk early.
- State, local file writes: once the new state file is linked and the folder synced, removing the temporary file and pruning old files are tidying: a failure there is logged (`knoggin-state` now depends on `tracing` for it) and the write succeeds; a file not pruned now goes at a later write.
- State, `knoggin state use-previous`: a newest file is set aside under `<name>.bad`, or `.bad.2`, `.bad.3` and on (up to 1000) when that name exists; the name is taken with a hard link that fails on an existing name, so a file set aside before is never replaced.
- HTTP, tests: a ghost for the `conflict` cases is made through the API (a namespace whose thresholds every sweep crosses, a memory created 30 days back, two close-and-open cycles, each open sweeping). The per-store request limit is filled with imports whose bodies never arrive; the request timeout is met with a backend whose open takes longer than the limit. Lock, upload-budget and lease cases inject the backend answer (`tests/support::Counting`); `master_key_missing` and `format_too_new` are also met through the real `LocalBackend` and snapshot reader.
- UI, `Store::view`: not added. The read models read the engine's existing public accessors (`memories`, `graph`, `namespaces`, `strengths`, `namespace_counts`), which a `StoreView` would only repeat.
- UI, next phase change: worked out from the forgetting curve as the sweep plans it (effective strength for full and summary, with the connection bonus as it is now; raw strength for a ghost), not with recalld's raw-strength `days_until_threshold`; a change already due reads as now (the next sweep).
- UI, strengths: `MemoryRow.strength` and the graph's `strength` column are raw strength at the time of the call, and `decayStrength` is effective strength (recalld stored both).
- UI, Health `atRisk` ("Fading soon"): the 10 memories that are not ghosts with the soonest next change, as `{ id, summary, strength, daysUntilChange, phase, to }` with the whole ID, because a Knoggin ghost has no text and cannot be reinforced; recalld listed ghosts nearest deletion with an 8-character ID.
- UI, Health `lastSnapshotBytes`: the size of the snapshot the store was read from, or of the last one written since; `null` for a store never saved.
- UI, search: each recall runs at `depth` 1 (recalld's search screen) with `fullTextCount` 0.
- UI, `GET /v1/ui/memories`: `limit` defaults to 200 (recalld's) and may be 1 to 200; `sort=lastAccess` orders a memory never accessed by its creation time.
- UI, activity: a `sweep` row is for the whole store and shows whatever the namespace filter; the sweep when a store opens makes no event (it runs before the store has its event log).
- UI, events: a `link` event names the client that saved the memory (the vector lands in the background); a sweep's `phase_change` and `forget` events have no client; a forced namespace delete sends a `forget` for each removed memory; a move, an import, `GET /v1/context` and the UI's own search send none.
- UI, system: `startedAt` is when the store host started (with the process, in practice); `rssBytes` is `VmRSS` on Linux and `null` elsewhere, because macOS gives it only through `unsafe` or a child process; `embedLatencyMs` is the median of the queue's document embeddings; `sweep.lastAt` is the last sweep of the open store (at open, then daily) and `nextAt` 24 hours later.
- UI, event stream cap: counted per user over every credential, and a stream also holds one of the user's 128 in-flight slots for its life, as an export does.
- UI, serving: `index.html` is `no-store` wherever it is served, `/index.html` included; a path with a `..` segment gets `index.html`; the content security policy goes on HTML answers only, with the hashes worked out once from the embedded `index.html` on first use.

- Sign-in, token times: `exp` and `nbf` are checked by `jsonwebtoken` against the system clock (60 seconds of leeway), which the library offers no way to replace; the signing-key cache, cookie sessions and the login cookie's `exp` use the edge's clock (`EdgeParts::clock`).

- Sign-in, ID token audience: the callback accepts an ID token whose `aud` contains the web client's ID (a list with another entry passes), as OpenID Connect allows; the spec says it "must be the client ID".
- Sign-in, `auth.email_claim`: an access token's `email` with `email_verified: true` is used first; the claim that `auth.email_claim` names is used only when that pair is missing.
- Sign-in, outbound client: in test mode the client follows up to 5 redirects and allows `http`; outside it follows none and sets `https_only(true)`. It keeps no idle connections, so a pooled connection never outlives the provider's address (the calls are rare).
- Sign-in, unavailable provider: a request with an access token while discovery has not worked, or while the keys are older than 24 hours, answers `unavailable` with `Retry-After: 60`; `GET /auth/login` answers `unavailable` too.
- Sign-in, the challenge: `error="invalid_token"` is added to every `unauthenticated` answer on `/v1` and `/mcp` whose request carried an `Authorization` header (an API key or a local session token as well as an access token); `/v1` answers point at the `/mcp` metadata address.
- Sign-in, cookies: the session and login cookies carry exactly the attributes of the cookie table and no `Max-Age` or `Expires`, so a browser drops them when it closes; the 7-day and 24-hour limits are enforced on the server either way. Clearing a cookie adds `Max-Age=0`.
- Sign-in, redirects: `/auth/login` and `/auth/callback` answer `303 See Other`. The callback clears the login cookie on every outcome; a state database failure during the callback answers the JSON error (with the cleared cookie) instead of `/signin?error=`.
- Sign-in, where a cookie is read: only on the router's public listener and the daemon's fixed listener; on the Unix socket and the local web listener a cookie is ignored.
- Sign-in, logout: `POST /auth/logout` (now the edge's own route, tag `session` in the OpenAPI document, which also ends a local web session on the web listener) runs the credential check first, so an expired cookie gets `unauthenticated` and is not cleared by it.
- Sign-in, a token without a verified email on a server: `permission_denied` with the message "Sign in at <public_url> once, then connect again" and no `reason`, with and without an allow-list.
- Sign-in, rate limits: an access token's bucket is keyed by the token's SHA-256 and a cookie session's by the cookie's, so an agent with a new token starts a new bucket.
- Sign-in, the fixed listener's bucket (step 1): on the daemon's fixed listener every request to a route that needs no credential (`/auth/login`, `/auth/callback`, the protected-resource metadata, `/healthz`, ...) takes from the bucket, whatever `Authorization` header or cookies it carries; a callback that ends in a sign-in gives its token back. The spec charges only requests with neither header nor cookie there, which let one login cookie and its `state` drive unlimited code exchanges (each a token-endpoint request with the client secret). Only the session cookie (`__Host-session`, or `knoggin_session` in test mode) counts as a cookie credential; a request with any other cookie, the login cookie included, is charged at step 1 as a bare one.
- Sign-in, where it is served on a local install: `/auth/login` and `/auth/callback` answer `not_found` on the daemon's fixed listener unless the `Host` is the host and port of `server.public_url` (the check behind the session's `webSignIn`), in test mode too, so no login or session cookie is ever set for `127.0.0.1`, `localhost` or `[::1]` unless that address is `public_url` itself. The spec states the outcome ("no cookie is ever set for a loopback address", "Web sign-in happens at that public address only") but not this check.
- Sign-in, discovery and key-fetch tests outside test mode: the stub serves `https` on 127.0.0.1 with a certificate from a test CA kept in `crates/knoggin-http/src/edge/testdata/` (made once with `openssl`, valid to 2126; the CA's key was not kept), and the provider under test is built with `test_mode` false and its real client settings (no redirects, `https_only(true)`) plus that CA as the only root. `rustls` and `tokio-rustls` (both in the dependency table) are dev-dependencies of `knoggin-http` for it.
- Sign-in, the signing-key cache: one fetch of the key set runs at a time, and the cache is locked only to read it and to store a result, never during the fetch. A token whose key ID is unknown waits for a fetch that is running (it may bring the key) and is not fetched for again; a token with a known key is checked against the keys held meanwhile, also when the hourly refresh is due and another request is doing it. The 30-second rule is unchanged: it counts from the start of the last fetch.
- Sign-in, admins: the admin check reads the stored verified email; a token's newer verified email is written first (bookkeeping write, `Users::note_email`) and used for that request whether or not the write won.
- Sign-in, session route on a local install: an access token reports `user.name` and `user.email` as `null` (the spec names only cookie sessions and `knoggin open` sessions).
- Sign-in, daemon discovery: the daemon runs discovery in a background task from the moment it goes live (at start, or when it unlocks from locked mode), so the socket and API keys serve at once, even while the provider takes the connection and never answers; the sign-in routes and access tokens answer `unavailable` until it works, and an unreachable provider is tried again once a minute. An issuer mismatch or an `http` address therefore never stops a daemon's start: it is logged with both values and sign-in stays off, as the spec says for a daemon that learns it after it has started. (The router, milestone 6, still refuses to start.)
- Sign-in, the router's guards: written as `edge::guard::{router_settings, router_users, check_public_url}` with unit tests; the router that calls them, logs the warnings and exits is milestone 6.
- Test issuer: the authorization redirect also carries `iss`; `POST /mint` answers the token as plain text; `rotate_keys` stops publishing the old keys but `mint_with` can still sign with them; `secrets()` returns every code, verifier, challenge, nonce, state and token it saw or made, for the log-marker test. `knoggin test-issuer` stops on SIGTERM or SIGINT. In process it also has `token_requests()` (how many requests reached its token endpoint) and `require_basic()` (from then on its discovery document lists only `client_secret_basic` and the token endpoint refuses a secret in the form), for the rate-limit test and the log-marker test's `client_secret_basic` run.
- Web UI, sign-in end-to-end run: `ui/e2e/signin.spec.ts` runs its own daemon (mode `oauth`, test mode) and `knoggin test-issuer`. `server.public_url` must name the fixed listener's port before it binds, so the harness picks a free loopback port for it (and for the issuer) just before start; another process could take it in between.
- Web UI, sign-in run, `account_removed`: a local install has one user, whom no admin can remove, so the daemon's callback never sends this code; the run opens `/signin?error=account_removed` directly and checks its sentence and that it has no Sign in button. The callback's side is covered by `knoggin-http`'s sign-in tests.
- Web UI, sign-in run, `provider_error`: the test issuer always approves, so the run keeps `/auth/login`'s real answer and its login cookie and replaces its `Location` with the callback a provider sends on an error (`error=access_denied` with the real `state`); Playwright cannot route the redirect to the issuer itself.
- Web UI, sign-in run, `not_allowed` and `email_unverified`: reached by opening `/auth/login` with a `login_hint` (`mallory`, `carol-unverified`), since the UI's button sends none. `carol-unverified@test.example` is on the allow-list, so her refusal comes from the unverified email.
- Web UI, `return_to` in the browser: where the UI follows `return_to` itself (the signed-in `/signin` and the sign-in button's target), it applies the server's rule (starts with `/`, second character neither `/` nor a backslash, no backslash, no control character) and uses `/map` otherwise; before, `/signin?return_to=//host` handed an off-site address to SvelteKit's `goto`.
- State database, Postgres, clock: `PostgresDb::connect(url, &state_keys, clock)` takes a `Clock`, as `LocalFileDb` does, because the conformance suite moves a `TestClock` to test expiry. The current time is always bound as a parameter (`$n`), never read from the server's `now()`.
- State database, Postgres, lock order: `write` applies its writes sorted by `(pk, sk)`, so that two writes naming the same items lock them in one order and cannot deadlock (the spec gives no order). A stack test runs 20 three-item writes in opposite orders at once.
- State database, Postgres, timeouts: the spec gives no numbers. A call waits at most 10 s for a connection (`acquire_timeout`), the server cancels a statement after 10 s (`statement_timeout`, sent at connect), and every call is bounded by 20 s on the client, so a silent connection cannot hold a request. Each ends as `StateError::Unavailable`.
- State database, Postgres, `sslmode`: the URL's own query is read for `sslmode` (or sqlx's alias `ssl-mode`, last one wins, as in the driver); `PGSSLMODE` in the environment does not count. The parsed options are checked again. A refused or unparseable URL is `StateError::Invalid`, whose message never quotes the URL.
- State database, Postgres, migration and housekeeping: `connect` never migrates; the router calls `PostgresDb::migrate`, so the lifecycle login (no `CREATE`) never tries. `PostgresDb::delete_expired` is the lifecycle task's "delete expired rows".
- State database, Postgres, errors: a driver error leaves as `Unavailable` carrying only the SQLSTATE code or fixed text (a database message can quote values, a connection error the URL); a row that does not decode or open is `Corrupt`.
- State database, Postgres, state key: `knoggin_crypto::MasterKeySet::derive_current(info)` was added, because the set kept its current key private.
- State database, Postgres, dependencies: `sqlx-postgres` brings RustCrypto's `hmac`, `hkdf`, `md-5` and `sha1` for SCRAM and MD5 password sign-in. The "do not add" list is about Knoggin's own code, which still uses only `aws-lc-rs`; `cargo deny` passes. sqlx 0.9.1 was resolved with a plain lock update on 2026-11-25, the day it became old enough, so the by-hand steps were not needed.
- Stack tests, image pins: testcontainers 0.28 always writes `<name>:<tag>`, so `stack_postgres.rs` passes the pin from `tests/images.toml` as name `postgres@sha256` and tag `<hex>`, which joins back into the digest reference.
- Stack tests, Postgres dump check: `stack_postgres.rs` reads every `doc` with `SELECT` and checks none parses as JSON or shows a field name; the `pg_dump` marker search of I14 belongs to the one-host stack test and is not done here.
- Server, link listener: the container's and the router's internal listeners pick HTTP/1.1 or HTTP/2 from the TLS ALPN result instead of hyper-util's automatic guess, so no read waits unbounded for a preface; the TLS handshake is bounded by the 30-second header read timeout. A client without ALPN (the `hello` call) gets HTTP/1.1.
- Server, link bodies: the bodies of `hello`, `claim`, `park` and `status` are shared types in `knoggin_server::link::api`, so router and container cannot drift; `knoggin_core::ops::ModelState` (with `ModelStatus` and `ModelUnavailableReason`) gained `Deserialize` for them.
- Server, link headers: the internal link's identity and token headers are read and written by new helpers in `knoggin_http::ctx` (`link_bearer`, `link_identity`, `link_protocol_ok`, `write_link_identity`, `write_link_bearer`) beside two new names, `CONTAINER_ID` and `INTERNAL_STATUS`. On the link the scheme must be written exactly `Bearer `: both ends are Knoggin.
- Server, certificates: a container's own certificate keeps rcgen's default validity (1975 to 4096), because the pin decides and nothing checks dates; `knoggin admin internal-cert` gets a 10-year certificate from `new_internal_cert(now)`, which takes the time as a parameter.
- Server, settings: `knoggin_server::settings` holds values with secrets already read (`InternalSecret`, `SecretText`), not the file's `_file` paths, which stay in the binary's config. `limits.per_address_*` and `limits.per_user_*` live in `RouterLimits` until the edge layer takes them. `Cidr` refuses a range written with host bits set (`10.201.3.0/16`), so a typo is not silently widened.
- Server, S3 presigning: the SDK's presigner (aws-sdk-s3 1.161) puts both `content-length` and `if-none-match` in `X-Amz-SignedHeaders` of an upload link, as a unit test checks, so `aws-sigv4` is not used directly. The returned headers leave out `Host`, which follows from the URL.
- Server, S3 errors: a service error keeps only its code (`StorageError::Refused(code)`); `SlowDown`, `InternalError`, `ServiceUnavailable` and every transport failure are `Unavailable`. Deletes go in batches of 1,000 in quiet mode; the first per-key error fails the call.
- Server, AWS config: `storage.credentials_file` is read through aws-config's `ProfileFiles` and `ProfileFileKind`, which aws-config offers only under deprecated aliases; the two uses carry `#[allow(deprecated)]` instead of adding `aws-runtime` as a dependency.
- Server, `MemoryStorage`: its links use S3's parameter names with values of its own (`X-Amz-Algorithm=KNOGGIN-TEST-HMAC-SHA256`, `X-Amz-Credential=memory`), path-style addresses `/knoggin-test/<key>`, and `x-id` as the SDK writes it. It signs the method, the path, every parameter but the signature and the signed headers' values (`host` always). It answers 400 to an unknown or repeated parameter and 412 to any upload of an existing name.
- Server, launcher: `ContainerInfo` carries a `RunState` with `Pending` beside `Running` and `Ended` (an ECS task being placed), and `LaunchError` is `Unavailable`, `Refused(reason)` or `NotFound`. `BuildInfo::compare` implements semantic-version order itself (pre-releases before releases, build metadata ignored); a version that does not parse compares as neither newer nor older.
- Server, router rate limits: the buckets per address and per user live in the edge layer (`EdgeConfig::per_address`, `per_user`), keyed by a `ClientAddr` that the router's public listener puts in each request. The fixed ceiling (ten times the rate) counts every public request, the web UI's files included. A request that sends a credential to a route that needs none is charged to the address bucket on the public listener too, as on the daemon's fixed listener.
- Server, relayed answers: `knoggin_http::error::Relayed` marks a container's answer, so that the edge's error shaping does not replace a container's JSON error body (a 404 or 500) with its own.
- Server, router listeners: `edge::listen::serve_tcp_admitted` (public and metrics listeners) admits by peer before reading and tags each request with `listen::Peer`; on one host it closes connections from peers outside `server.trusted_proxies` and loopback.
- Server, `status` on a new connection: `link::fresh_client` keeps no idle connection, so every `status` call (after a failure, a silence, the store status, the stuck-claim step and the counters step) opens its own.
- Server, forwarding: a body is buffered when its exact length is known (a `Content-Length`) and at most 1 MiB, within the 256 MiB and 16 MiB allowances; an HTTP/2 body without a length is streamed. The ordinary request timeout runs until the response headers arrive; after that only the silence rule applies. A parking container is waited for only within the request's claim deadline.
- Server, Mark gone: after asking for a stop, the router describes the container once more and finishes the routine at once if the launcher already shows it ended (the Docker launcher's stop waits for the exit). On ECS a task the API does not know is answered `unavailable` with `Retry-After: 2` on the request path.
- Server, claims: a claim also skips `ready` containers that started before `retire_before_ms`, so that one is not claimed between reconcile passes. A refused launch marks the record `gone` without a `stop_reason`.
- Server, rollout: the leader launches the first container of a new desired build at once and later ones at most once a minute. `knoggin_rollout_stalled` is 1 while claims have not switched and a desired-build container ended with `launch_failed`; on one host it is 1 while the last checked `hello` reported another build than the one launched, and launches then go at most once a minute.
- Server, metrics: `knoggin_launches_total` (`outcome`: started, refused, failed, ready) is the metric that counts refused launches; the container counters are published with `Counter::absolute`, since their sums fall when a container ends.
- Server, the router's mode routes: built with `serde_json` in `knoggin_server::router::status`, in the daemon's shapes (the shape types are private to `knoggin-http`). The store status answers `waking` for a `claiming` lease and for a warm container that does not answer in 2 seconds. The admin status counts users by walking the user directory.
- Server, reconcile step 3: before stopping a `claimed` container whose user's lease does not name it, the router reads that lease again, since the pass's list of leases can be older than the record.
- Server, address reuse: the older records at a reused address get "Mark gone" without a `stop_reason`, so their end is what the launcher reports.
- Server, panic guard: the outer layer makes the request ID and opens the span; the edge layer reuses that ID (it reads an existing `RequestId` extension), so the panic line, the error body and the header carry one ID.
- Server, router start-up: `knoggin_server::router::guards` adds the one-host checks to `edge::guard::router_settings`; the binary runs the state database, schema, field key, users check, discovery, self-test and `attach` steps and then `rollout::at_start` and `router::run`, which serves.
- Server, container role: `knoggin_server::container::{serve, serve_on}` return `ServeEnd { exit_code, reason }` with `EndReason::{Parked, Stopped, LeaseLost, Failed}`; exit code 0 after a park or a stop of an unclaimed container, 1 after `lease_lost` or a failed start. `serve_on` takes a bound listener so the fleet tests can use port 0. `container::runtime()` builds the role's runtime with `max_blocking_threads(128)`.
- Server, container model: `ServeModel` carries the model identity, the state channel and the providers; `ServeModel::fake()` is test mode's and keeps its own state sender alive.
- Server, container waits: the park drain (30 s) and the retry of a standing park request (60 s) are fields of `ServeTimings` so in-process tests can shorten them; the store host cannot run under paused time.
- Server, `hello`: a nonce the container has answered (it keeps the last 64) is refused with `conflict`; `hello` without `Knoggin-Protocol` is `internal`, as every internal call.
- Server, container refusals: a forwarded request without a valid router token is `unauthenticated` (401), which the router turns into `internal`; a forwarded request for another user, or to an unclaimed container, is `internal`; `/internal/*` with `Knoggin-User-Id` is `not_found`.
- Server, 64 MiB of bodies in flight: a request reserves its `Content-Length`, nothing when it has no body, and `limits.body_bytes` (the largest body the store layer buffers) when its length is unknown; the reservation is held until the store layer's handler returns. `POST /v1/import` streams ("no limit on the whole body"), so it reserves at most 4 MiB (`IMPORT_LINE_BYTES`, one line), whatever its length; an import of more than 64 MiB goes through. The host can hold a little more than that for one import (a parsed batch of up to 1 MiB beside a line being read); that is accepted.
- Server, park step 1: a request that outlives the 30-second wait gets `unavailable` if its handler is still running; an answer that is already streaming (an export) is broken off. After a failed park the container serves again, but its event streams stay ended until the next process (`StoreHost::end_event_streams` is one-way); the web UI then gets 204 and subscribes again later.
- Server, park retries: after a failed park, the next idle try waits `idleSeconds` from the later of the last request and the failed try; a standing router request is tried every 60 s. After a stop signal the snapshots are tried with back-off (1 s doubling to 60 s) until they succeed.
- Server, `RouterBackend`: a commit that fails after its upload went through is kept in memory and committed again before that store's next save; if the host retries the same name, that commit is sent and the save answers `NameTaken`, so the newer changes take the next sequence. A broker 429 without a reason is tried again up to 5 times (250 ms doubling), then `unavailable`. Each broker call has a 30-second limit; snapshot transfers end after 60 s without bytes.
- Server, which client sends a link: a link under `KNOGGIN_ROUTER_URL` + `/internal/v1/blob/` goes over the pinned link with the container's identity headers; any other goes to the bucket with `reqwest` (no redirects). The container decides by the broker's error code in the body, never by the bare status: only `lease_lost` (`LeaseLost`), `store_deleting` and `not_found` (`Deleted`), `store_locked` and `rate_limited` with `upload_budget` mean anything but `unavailable`. The blob route passes on a bucket's success and its 412 (the name exists, `NameTaken`); every other bucket status becomes the broker's own 503 `unavailable`, so a bucket's 404, 410 or 409 never drops a store or ends a lease. A bucket's refusal on a direct link (AWS) is `unavailable` too.
- Server, broker errors: `BrokerCode` is `Api(Code)` or `LeaseLost`; the body is the REST shape without `field` and `requestId`. A missing or wrong token or identity headers is `lease_lost` and counts as a failed token for the peer address; a missing protocol header is `internal`. `unavailable` carries `Retry-After: 2`.
- Server, broker bodies: an empty `open` body is `{}`; unknown fields in `open`, `snapshots` and `commit` bodies are `invalid_argument`. Request bodies are read up to 1 MiB without a `RequestBodyLimitLayer` (the handler reads them itself, after the caller's checks).
- Server, broker limits: per-container calls (4 in flight, 600 a minute) and per-address connections (60 a minute) use fixed one-minute windows; the hourly upload and download budgets slide over the last hour. Download bytes are counted as they stream. `PeerLimits` is shared by the broker and the listener's `admit`, and `PeerLimits::clear(ip)` is for a new container at an address.
- Server, broker `open`: a restore whose named object is missing, or an `after` during a restore, is `store_locked` (`snapshot_unreadable`). The lifetime park request for a name ahead of the lease is written with the lease's `Version(n)`; a lost race is left to the next open.
- Server, broker `commit`: `restore_from` is cleared only by a commit that raises `newest`; a commit for a lower name changes nothing, as the spec says. The commit does not check that the object exists.
- Server, blob route: the bucket address is taken from a fresh signature of the same object by the router's own `ObjectStorage` (only the part before the query is used), so path-style and virtual-host addressing need no code of their own. Besides the four link headers, `Host` is never passed on; the router's HTTP client may add `accept`. The idle rule is applied per direction (60 s without a chunk on the upload stream, and on the download stream).
- Server, `parked`: the broker checks the caller, then runs `BrokerConfig::on_parked`, the router's own "Mark gone" steps 2 to 4 and stop, which the router wiring supplies.
- Server, one set of per-address bounds: the router's own copy was removed; the broker's `PeerLimits` (held by the fleet) is the internal listener's `admit`, takes the broker's failed tokens, and is cleared on an address reuse. The broker's fallback answers 404 off its routes, so no separate wrapper is needed.
- Server, router entry point: `router::run_router(RouterStart, stop)` takes the state database already connected (and, on Postgres, migrated) and the listeners' sockets bound but not listening (`router::reserve`): the binary takes the ports before it connects to anything, so a port in use stops the start at once, and `router::run` makes them listen as start-up step 10, so nothing can connect before the other steps are done (on macOS a connection to such a socket goes unanswered rather than refused); the bucket self-test and `DockerLauncher::attach` (steps 7 and 8, not built yet) come in as one `before_rollout` future. Discovery that cannot reach the provider is tried again every 2 seconds for 60 seconds (`forward::Timing::discovery`, shortened to 2 seconds in the fleet test), after which the router exits with code 1; other discovery errors stop the start at once. A router outside one host refuses to start without `internal.router_url`.
- Server, fake launcher: each fake container runs on a Tokio runtime of its own (one thread), so that a kill ends every task it spawned and frees its port, as a process's end would; `stop` waits `stop_grace` (10 s) for the role to return before it kills it.
- Server, fleet tests: they run with one host on (except the rollout test, which needs `claim` and `desired`) and a test-made fleet that takes leadership to run reconcile passes on demand; the routers' own loops keep running beside it, since every step is safe to repeat. Checks that need a container on its own address (I6 from another address, the flood test, failed tokens before an address reuse) run on Linux only and print why they are skipped elsewhere.
- Server, lifecycle thinning: objects under a store's `snap/` folder whose names are not snapshot names are left alone, and a store counts as not deleted by its own mark only (a store of a deleted user is thinned until it is erased with the user). The stores to thin are read without the field key by `knoggin_state::thin_targets`.
- Server, I11 test: "only the lifecycle task deletes objects" is a unit test that scans `crates/knoggin-server/src` for `.delete(` (other than `containers.delete(`), `ObjectStorage::delete` and `delete_objects` outside `lifecycle.rs` and `storage/`.
- Server, restore in the host: a store opened with `restore: true` takes no client write (`unavailable`, `Retry-After: 2`) and no import line until its first commit succeeds; bookkeeping (access recording, embeddings) goes on, since it lands in that same snapshot. The first save is started at once (with a 500 ms back-off seed) and runs even when nothing changed.
- Server, `admin restore`: a store that does not exist, or a snapshot that is not in the bucket, is refused (exit 1). The park request is written on the lease as the reconcile loop would (kept if one stands). `--snapshot` takes 1 to 10 digits per number. The wait polls the lease every second.
- Server, `admin retire-before`: refused when no router has written the rollout record yet; it then counts the active-lease items. A time is RFC 3339.
- Server, `admin rotate-master-key` on one host: the key set file is replaced first (temporary file, sync, rename, then mode 0444), then the field key and every store's data key are wrapped again; a run that stops after the file can be repeated. With `keys.provider = "kms"` it prints that KMS rotates its own key material and exits 0 without connecting.
- Server, `admin selftest`: the database check is `Meta::check_schema` (one read of the schema record, which writes it only if it is missing). Output fields: `stateDatabase`, `keyProvider`, `bucket` (`ok` or why) and `passed`.
- Server, bucket self-test: step 3 runs on a fresh name, so that only the signature can refuse its three uploads; each upload sends every signed header except `Content-Length`, which the HTTP client sets from the body. `MemoryStorage::weaken` takes away one property at a time for the tests (an edit to the test stand-in).
- Server, launcher service: a stop answers 204 once the stop is asked (the 120-second wait runs as an owned task); `endReason` is `stopped` for a container the launcher was asked to stop (kept in memory, so after a launcher restart such a container reads `exited`), `memory` when Docker reports `OOMKilled`, `exited` otherwise. A handle or another stack's container is `404` alike. A labelled network's "no user container for a minute" is counted from the first tidy pass that sees it empty, in the launcher's memory. A create needs the router's container to be running (503 otherwise). Request bodies are at most 16 KiB and refuse unknown fields.
- Server, `DockerLauncher`: a 400, 401 or 503 from the service is `LaunchError::Refused`, a 404 `NotFound`, anything else or no answer `Unavailable`; each call has a 30-second limit; a handle that is not alphanumeric is `NotFound` without a call.

- Server, launcher service tidy-up: it now takes the router off a network before removing it also when the router's container is stopped (it looked for a running one only). Docker removes a network that only a stopped container names, and that container then cannot start ("network not found"), so `docker compose stop router` followed by `start` failed about one time in three once the parked containers' networks were tidied away. If the router cannot leave the network, the network is kept for the next pass. The fake Docker in `tests/launcher.rs` now refuses a network removal only for a running member, as Docker does.
- Server, broker check order: protocol, container token, then the lease (container, state, address), and only then the per-container call slot, so a launch secret used from another address than the lease's takes nothing of that container's 4 in flight or 600 a minute.
- Server, park drain: a forwarded request is counted as activity before the container reads its phase, so a park that saw no request in flight has already set `parking` for any request that comes after; such a request is answered with the parking status and counts only while it is refused. The race test checks that the park's snapshot holds exactly the acknowledged writes; it cannot force the old interleaving, so it passes on the old code too.
- Server, blob route `Content-Length`: the outbound headers are built in one map (`outbound_headers`), the signed headers once each and `Content-Length` once, from the checked value. The test checks the request as `reqwest` hands it to hyper, which writes every value in the map; `MemoryStorage` cannot show a duplicate itself, because hyper's server drops a second `Content-Length` of the same value before the handler sees it.
- Server, object-storage timeouts: every `S3Storage` client gets connect 5 s (`CONNECT_TIMEOUT`), read 30 s, 30 s per try and 60 s per call with its retries; a listing is one call per page, so a listing of many pages is bounded per page. Presigning makes no network call.
- Server, restore test (`a_restore_opens_the_chosen_snapshot_and_saves_it_before_any_write`): it raced, the code did not. The broker clears `restore_from` in its commit before the container has the answer, and after a retried commit the host saves once more under the next sequence (`NameTaken`), so the container lifts its write block one upload later. The test now waits for a write to be accepted, and checks that every refusal before that is `unavailable`. Before: 7 of 40 runs failed with 503; after: 50 of 50 passed.
- Server, launcher service: a container that Docker created but could not start is removed at once (force), so it never stays `created`; its network is then empty and the tidy-up removes it after a minute, which frees its /29.
- Server, link listener and HTTP/2: after the TLS handshake an HTTP/2 connection must bring its first request within the header read timeout (30 s), or it is closed; hyper's HTTP/2 server waits for the client's preface without a limit and its keep-alive starts only after it. This bounds the first request, not only the first frame, which a link client always sends at once.
- Server, a refused peer address: while an address is refused for failed tokens, every broker call from it, also on a connection opened before the refusal, is answered 429 `rate_limited` without a reason (the container backs off and retries), before any token is checked. New connections are still closed without an answer.
- Server, `parked` from the container: 3 tries, each with a 2-second limit and a 2-second pause between, so at most 10 seconds in all. An answer with the code `lease_lost` marks the lease lost, is not tried again, and the container ends as `LeaseLost` (exit 1) rather than `Parked`.
- Server, owned tasks in the container and launcher: the `spawn_blocking` task that seals an upload's chunks is joined once the upload has sent or dropped its body, within the 60-second transfer bound; the launcher service aborts its server task if it outlives the 5-second shutdown wait. A failed lifecycle pass logs only which part failed (`state` or `bucket`), not the error's text.
- Server, test stand-in: `MemoryStorage` has `Fault::Answer(status)`, which answers every HTTP request with that status and no body while `list` and `delete` keep working, so tests can give the blob route a bucket's 404, 410 or 409.
- Server, reconcile leadership: the leader record is renewed every 10 seconds also while a pass runs (the pass is polled beside the renewal), so a pass longer than the record's 30 seconds keeps it. When a renewal fails, or cannot be checked because the state database fails, the pass is dropped where it stands (every step is safe to repeat) and the leader's memory (the counts of passes that missed a container) starts afresh; a stop ends a pass the same way.
- Server, router stop: the public and metrics listeners stop accepting and the reconcile loop is aborted first; on one host every claimed container is then asked to park all at once (the `park` calls run side by side, each with its 10-second limit), and the requests in flight on the public listener finish. Both waits end together 110 seconds after the stop (`Timing::shutdown_wait`), also on AWS, where only the requests in flight are waited for; whatever still runs then is cut off. The internal listener closes after that wait (with 5 seconds for its own requests, then it is aborted), and `run_router` returns only once every task it spawned, the fleet's launches and claims included, has ended. The fleet test checks this by counting the live tasks of the router's own runtime.
- Server, reconcile step 4 on ECS: the leader counts the passes whose list did not show a `starting` record's container, as step 2 does for `ready` and `claimed` ones, and a `starting` record past the 120-second launch limit that two lists in a row missed has ended (as `failed`, since no container ran to take a `stop_reason`). So a router that died between writing `starting` and calling `launch` does not hold claims of that build forever; one whose launch is merely slow is still inside the 120 seconds and untouched.
- Server, reconcile errors: a step, or one lease or container within a step, that the state database fails is logged and counted in `knoggin_reconcile_errors_total` (label `step`, a counter the spec does not list), and the pass goes on with the next one. Only the first reads (step 1) end a pass early, since nothing after them has anything to work on; a failed rollout step skips the pool step, which needs its claim build.
- Server, client address: walking `X-Forwarded-For` from the right, an entry that does not parse as an address (or a header value that is not text) ends the walk with the peer's address, so that a client cannot hide behind a malformed entry and have an address it wrote further left taken instead.
- Server, `knoggin_rollout_stalled`: a container record of the desired build that is `gone` without a certificate pin (it never passed `hello`: refused by the launcher, failed, or out of time) marks the rollout stalled, so a refused launch, whose record carries no `stop_reason`, counts too. `metrics-exporter-prometheus` (already in the workspace) is a dev-dependency of `knoggin-server` so that a test can read the gauge.
- Server, claims: the request path reads the container records at most once per 250 ms per router and shares that read among all waiting requests (there is no index by state to narrow the query); a claim write, won or lost, and a launch drop it, so a request never meets the same stale candidate twice. A stale read can at worst make a request wait one more 250 ms.
